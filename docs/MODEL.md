# 모델 설명 (v9c)

[README](../README.md)로 돌아가기 · [API](API.md) · [이어 학습](TRAINING.md)

NotiAI 서비스가 쓰는 일정 추출 모델의 입력·출력, 구조, 학습 데이터, 학습 방법, 후처리, 평가 방법과 결과, 버전 이력을 정리한다.

## 1. 하는 일

공지 1건(제목, 본문, 게시일)을 받아 **학생이 직접 행동해야 하는 일정** 목록을 JSON으로 돌려준다. 일정 선정 기준은 [README의 "무엇을 일정으로 뽑나"](../README.md#무엇을-일정으로-뽑나)와 같다. 모델은 일정을 뽑기만 하고, 화면에 무엇을 보여 줄지(대표 일정, 캘린더 자동 등록 여부, 알림)는 백엔드가 정한다.

## 2. 입력

서버는 요청의 `title`, `body`, `reference_time`으로 아래 형식의 사용자 메시지를 만든다(`model_server/slim_v1.py`, `model_server/prompt_input.py`).

```
[공지 제목]
2026 학생 아이디어 공모전 참가자 모집

[입력 메타데이터]
{"reference_time": "2026-10-19", "default_timezone": "Asia/Seoul", "input_issues": []}

[출처 title | title]
2026 학생 아이디어 공모전 참가자 모집

[출처 body | body]
접수기간: 2026년 11월 3일(월) ~ 11월 14일(금) 18:00까지 ...
```

- 시스템 프롬프트(`model_server/prompts/system_prompt.txt`, 약 3,300바이트)에 일정 정책, 출력 형식, 날짜·시각 규칙이 들어 있다. 학습과 서비스가 같은 프롬프트를 쓴다.
- `reference_time`(게시일)은 연도 없는 날짜의 연도를 정할 때만 쓴다. 없으면 연도를 추정하지 않는다.
- 첨부파일(PDF, 이미지)은 입력하지 않는다. 입력이 문맥 한도를 넘으면 자르지 않고 오류로 돌려준다.

## 3. 출력

```json
{"events": [{"event_type": "application", "title": "...", "start_date": "2026-11-03", "end_date": "2026-11-14",
             "start_time": null, "end_time": "18:00", "location": null, "attendance_mode": "not_applicable"}]}
```

| 필드 | 값 |
|---|---|
| `event_type` | `application`(신청·접수), `submission`(제출·납부), `event`(참석 행사), `interview`(면접) |
| `title` | 일정 제목 |
| `start_date`, `end_date` | `YYYY-MM-DD` 또는 null. 마감만 있으면 `start_date`는 null, 당일 행사는 둘이 같다 |
| `start_time`, `end_time` | `HH:MM` 또는 null. 그 일정에 적힌 시각만. 24:00은 다음 날 00:00 |
| `location` | 방문·현장 장소 또는 null |
| `attendance_mode` | `offline`, `online`, `hybrid`, `unknown`, `not_applicable` |

일정이 없으면 `{"events": []}`이다. 서버 응답 형식(상태, 검증 오류, 메타데이터)은 [API.md](API.md)를 본다.

## 4. 모델 구조와 생성 설정

| 항목 | 값 |
|---|---|
| 기반 모델 | Llama-3.1-8B-Instruct |
| 양자화 | 4bit NF4, double quantization, 계산 bfloat16 (QLoRA) |
| LoRA | r=32, alpha=64, dropout=0.05, 대상 q/k/v/o_proj, gate/up/down_proj |
| 생성 | greedy(샘플링 없음), 최대 1,024토큰, 문맥 12,288토큰, 생성 60초 제한 |
| 실행 환경 | GPU 1장(RTX 5070 Ti 16GB 기준 공지당 평균 7.3초, p95 17.9초) |

## 5. 학습

- **시작점**: 7월 모델 v10의 LoRA(충북대 공지로 학습한 단일 일정 5필드 모델)에서 새 옵티마이저로 이어 학습한다.
- **설정**: 3 epoch, 학습률 5e-5, 배치 1 × gradient accumulation 4, warmup 10%, weight decay 0.01, seed 42, 최대 4,096토큰(자르지 않음), 정답(assistant) 부분만 손실 계산.
- **체크포인트**: 마지막 체크포인트를 쓴다(검증 손실로 고르지 않음). v9c는 729 step, RTX 5070 Ti에서 81분.
- 명령과 데이터 형식은 [TRAINING.md](TRAINING.md)를 본다.

## 6. 학습 데이터 (v9c)

| 구분 | train | validation |
|---|---:|---:|
| 기존 데이터(충북대 중앙·RISE·학과 공지, 대외활동·공모전) | 790 | 26 |
| 서비스에서 수집한 실제 공지(2026년 10월) | 127 | 11 |
| 대비 공지(일정 없는 공지, 제외 대상이 섞인 공지) | 54 | 6 |
| **합계** | **971** | **43** |

- 일정 없는 공지 비율은 train 12.4%, 공지당 평균 일정 1.36개다.
- **정답 작성**: 정책 문서를 기준으로 LLM 에이전트가 원문을 읽고 일정마다 근거 구절(원문에서 그대로 복사한 문장)을 달아 작성했다. 이후 기계 점검(근거 구절이 원문에 있는지, 날짜 형식, 시작 ≤ 종료, 결과 발표·시상 같은 제외 대상이 없는지)과 서버 검증기(원본·후처리) 전체 통과를 거쳤다.
- **라벨 정정**: v9c에서 기존 데이터 25행의 정책 위반 일정 38개(장기 활동 기간 16행, 시상 5행, 운영 기간 3행 등)를 지웠다.
- **평가셋 분리**: 평가 공지와 URL, 정규화 제목, 본문 3-gram 포함률 0.65 이상 중 하나라도 겹치는 공지는 학습에서 뺐다.
- 학습 데이터와 정답은 공개하지 않는다.

## 7. 서버 후처리

모델 원시 출력은 그대로 보존하고, 서비스에 쓰는 후보에만 아래를 적용한다(`model_server/slim_v1.py`).

- 잘못된 달력 날짜는 그 필드만 null, 종료가 시작보다 앞서면 종료일만 null로 바꾼다. 날짜가 사라진 필드의 시각도 지운다.
- 시작·종료 날짜가 모두 없는 일정은 뺀다.
- 온라인 일정의 매체 이름·placeholder 장소는 null로 바꾸고, 실제 장소가 있으면 남기고 참여 방식을 `unknown`으로 둔다.
- 새 날짜나 장소를 만들어 넣지 않는다. 서버는 모든 결과에 `review_required=true`를 붙인다.

## 8. 평가 방법

**채점** (`공지 1건 = 정답 일정 목록과 모델 일정 목록 비교`)
- 일정 유형을 마감(`application`·`submission`), 참석(`event`), 면접(`interview`) 세 묶음으로 나누고, 같은 묶음 안에서 날짜·시각·장소가 가장 많이 맞도록 정답과 예측을 1:1로 짝짓는다.
- **재현율** = 짝지어진 일정 / 정답 일정, **정밀도** = 짝지어진 일정 / 예측 일정.
- **날짜·접수 마감일·장소·시각 정확도**는 짝지어진 일정 중 그 값이 정확히 같은 비율이다(시각은 정답에 시각이 있는 일정만).
- **공지 완벽 일치**는 일정 수가 같고 모든 일정의 유형·날짜·시각·장소가 맞는 공지의 비율이다. 제목과 참여 방식은 채점하지 않는다.
- **안전 지표**: 원문에 없는 월·일을 만든 공지 수, 무효 응답(JSON 오류·시간 초과) 수, 일정이 없어야 하는 공지에 일정을 만든 수.

**평가셋**
| 이름 | 공지 | 용도 |
|---|---:|---|
| 개발 평가셋 | 184 (135 + 49) | 오류 진단과 후보 선택. 개발에 반복 사용 |
| 독립 평가셋 v3 | 100 (채점 85) | 최종 판정 1회. 2026-10-18 이후 게시 공지, 학습·개발에 쓰지 않음 |

**정답 작성과 판정 절차**
1. 평가 공지를 먼저 떼어 봉인하고, 정답을 다 만들기 전에는 모델을 돌리지 않는다.
2. 서로의 결과를 보지 않는 두 개의 독립 라벨링 세션(LLM 에이전트)이 원문과 정책만 보고 정답을 쓴다. v3의 판정 전 일치율은 공지 단위 83%, 필드 단위 91.5%였다.
3. 별도 판정 세션이 두 정답이 다른 곳만 원문과 정책으로 판정한다. 원문으로 정할 수 없는 공지(날짜가 첨부·외부 페이지에만 있음, 학생 대상이 아님 등)는 채점에서 뺀다.
4. 채점 코드와 채택 기준은 모델을 돌리기 전에 문서와 해시로 고정하고, 결과를 본 뒤 바꾸지 않는다.

**v9c 채택 기준** (v9 대비, 모두 충족해야 교체)
- 공지 완벽 일치가 ceil(5% × 채점 공지 수)건 이상 많고, v9c만 맞힌 공지가 v9만 맞힌 공지보다 많다.
- 재현율, 정밀도, 날짜, 접수 마감일 정확도가 각각 v9보다 3%p 넘게 떨어지지 않는다.
- 안전 지표가 v9보다 나쁘지 않고, 생성 완료 100%, 공지당 p95 30초 이하.

## 9. 결과

독립 평가셋 v3(85건, 서버 후처리 후). v9c가 모든 채택 기준을 통과해 서비스 모델이 됐다.

| 지표 | v9 | v9c |
|---|---:|---:|
| 공지 완벽 일치 | 54.1% (46) | **61.2% (52)** |
| 일정 재현율 | 78.0% | **83.7%** |
| 일정 정밀도 | **93.2%** | 91.5% |
| 날짜 정확도 | 91.8% | **95.8%** |
| 접수 마감일 정확도 | 94.0% | **96.5%** |
| 장소 정확도 | **90.9%** | 89.0% |
| 시각 정확도 | 81.5% | **94.9%** |
| 원문에 없는 날짜 공지 / 무효 / 빈 공지 일정 | 2 / 1 / 1 | 1 / 1 / 1 |
| 공지별: v9c만 완벽 / v9만 완벽 | | 8 / 2 |

- v3는 공모전 공지가 86%이고 공지당 일정이 1.7개라 어렵다. 공지 1건이 약 1.2%p다.
- 개발 평가셋(184건)에서는 공지 완벽 일치 v9 132건 → v9c 141건, 접수 마감일 93.2% → 96.6%였다.

## 10. 버전 이력

| 버전 | 시기 | 내용 | 결과 |
|---|---|---|---|
| v10 | 2026-07 | 공지 1건 → 일정 1개, 5필드(제목·시작·종료·장소·설명) | 여러 일정·면접 단계를 표현 못 함. 이후 모델의 시작점 |
| slim v1~v6 | 2026-10 초 | 일정 여러 개 + 유형 8필드 형식으로 전환, v10 데이터 재사용 비율 조정 | 시연용 v6 |

## 11. 알려진 오류와 서비스 대응

| 오류 | 예 | 서비스 대응 |
|---|---|---|
| 일정 누락 | 본문이 짧고 날짜가 제목에만 있는 행사 | 상세 화면에 원문 링크, 사용자가 일정 추가·수정 |
| 불필요한 일정 | 선택 행사나 안내일을 일정으로 뽑음 | 사용자가 삭제, 신고 |
| 접수 마감일 오류 | 연장 공지, 회차별 마감 | 공모전 사이트의 접수 마감일과 다르면 "확인 필요" 표시 |
| 제목 글자 오류 | 고유명사 한 글자가 바뀜 | 채점 대상이 아님, 사용자가 수정 |
| 첨부 속 일정 | PDF·이미지 안의 날짜 | 읽지 않음 |
